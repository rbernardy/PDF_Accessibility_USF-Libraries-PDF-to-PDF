* Note: This documentation is a work in progress. The installation process is currently being validated against a newly created (empty) AWS account.
* This software must be deployed from a Linux environment. Fedora Workstation is highly recommended. All deployment scripts are Bash shell scripts executed from a terminal. (Future goal: provide a Fedora Remix tailored for this fork, to be released in a separate repository).
* These instructions assume you already have access to an AWS account. It is strongly recommended that you use a new/unused account dedicated to this deployment.
* The AWS CLI must be installed and configured prior to deployment. The installation process installs other dependencies.
* You must create an AWS CLI profile (e.g., aws configure --profile MY_PROFILE_NAME) for the AWS CLI tool. While authentication via an IAM user with administrative privileges is supported, use of an access key is recommended. During profile creation, configure the following values: access key ID, secret access key, default region, and output format. The output format must be set to json, as required by the deployment scripts.
* Copy the set-template.sh script to a location outside of the repository (e.g., your home directory) and rename it. Suggested naming convention: set-[institution abbreviation][first three digits of AWS account ID].sh (example: set-abc123.sh).
* Update your script with all required values, including the Adobe PDF Services API credentials (client ID and client secret). These credentials must be generated via the Adobe Developer Console after obtaining access and provisioning API usage credits.
* This script initializes all required environment variables and navigates to the root directory of the repository.
* Execute ./run-first-generate-public-bucket-name.sh, passing the path to your set script as the only argument.
* This script generates a random AWS_DESTINATION_BUCKET_NAME value, which serves as the 'public-facing' S3 bucket for accessing remediated PDFs. Access permissions must be configured manually via the AWS S3 console. The script automatically updates your set*.sh script with this value and stores it in ~/destination_name.txt for reference. This step is performed once during initial setup.
* For initial deployment (CDK bootstrap and deploy) to a new AWS account execute ./usfl-custom-initial-deployment.sh ~/path-to-your/set-*.sh. This script is intended to be run only once.
* Once the initial deployemnt tasks are completed this script will automatically invoke ./usfl-custom-cdk-deploy-redeploy.sh, completing deployment of the application. During this process, the AWS_PROJECT_S3_BUCKET_NAME value is generated and written back to your set*.sh script.
* After the initial deployment use ./usfl-custom-cdk-deploy-redeploy.sh for all subsequent redeployments to the same account, like when updating the application, for example.
* Redeployment does not modify or remove the project S3 bucket or its existing contents.
* One ssm parameter that does not get set automatically is the sender-email since the /pdf-processing/email-enambled defaults to false. Run the ./bin/set-sender-email.sh script to set that and then run the ./bin/set-email-enabled-ssm-parameter.sh script true to enable that feature.
* When you are ready to have the system start processing pdfs, drop pdf files into the queue folder of the project S3 bucket and then run the ./bin/queue-resume.sh script. Similarly, execute the ./bin/queue-pause.sh to pause the queue. These scripts only affect the operation of the queue, once files have been moved from the queue to the pdf folder, processing will occur/continue, regardless if the queue is paused or not.
* You can 'tune' the performance of the enhanced application via 17 SSM parameters. One script sets most of them - ./bin/set-all-ssm-parameters.sh. It is initially run by the ./usfl-custom-cdk-deploy-redeploy.sh script. That script runs it with the '--defaults' argument. This will set all ssm parameters to their default values, those that are not otherwise set during the initial cdk deploy process. 
* You can run the ./bin/view-current-ssm-parameters.sh script to list all 17 of the current ssm parameters and their values.  
* There are 'set-' scripts to so you can change the ssm parameters individually.
